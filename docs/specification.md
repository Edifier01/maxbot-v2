# Техническая спецификация MAXBOT v2

## Назначение и пользователи

Однопользовательская приватная панель для недельного расписания MAX-сообщений. Логин владельца задаётся установкой (`edifier8989` по умолчанию), хеш пароля — через интерактивный хешер. Форма входа не содержит предзаполненных учётных данных и просит браузер не выполнять автозаполнение. Пароль хранится как bcrypt-хеш; cookie — HttpOnly/Secure/SameSite Strict; изменения требуют CSRF-токен и проверку Origin. Регистрации, роли, организации и подписки отсутствуют.

## Группы, аккаунты и подключения

Группа содержит имя, MAX invite link, закреплённый chat ID, статус и собственные прокси. MAX-аккаунт принадлежит одной группе. Владелец может создать, заменить и отозвать гостевую ссылку с ограниченным сроком и числом запусков. Гость указывает имя и телефон, вводит OTP и, если потребуется, облачный пароль MAX, затем сам вступает в группу. Приложение не вступает вместо него, а проверяет членство.

Первый успешно авторизованный номер задаёт chat ID группы через PyMax; следующие должны подтвердить ту же группу. Смена MAX invite link отзывает гостевую ссылку, отменяет незавершённые подключения и сбрасывает chat ID до новой проверки. Сессия подключения живёт до 15 минут; после перезагрузки браузер восстанавливает шаг по ID попытки из `sessionStorage`. Код и пароль там не хранятся. Истёкшую или неудачную попытку можно запустить повторно для того же `pending`-аккаунта.

## Прокси

Перед авторизацией прокси назначается из пула группы: по минимальной текущей нагрузке, при равенстве — по меньшему `position`. URL шифруется Fernet-ключом, UI показывает безопасную подпись и состояние назначения. В гостевой авторизации только один запрос SMS-кода (`request_code`) выполняется напрямую. Перед ним назначение прокси должно существовать, быть включено, а URL — успешно расшифрован; иначе сценарий останавливается до запроса кода. Для запроса используется временный PyMax-клиент с отключённым прокси и `persist_session=False`; ответ челленджа остаётся только в памяти процесса. Проверка OTP (`send_code`), 2FA (`check_password`), установление и сохранение сессии, проверка членства и все остальные действия выполняются через назначенный прокси. Ошибка прокси не вызывает прямой переход; неопределённый результат запроса кода не повторяется автоматически.

## Расписание и отправки

Неделя — понедельник–воскресенье в настраиваемой тайм-зоне (по умолчанию `Europe/Moscow`). День назначается один раз по наименьшей загрузке. Максимум — одно подтверждённое MAX-сообщение на аккаунт за неделю. На группу запускается одна последовательная worker-задача; разные группы могут работать параллельно. Истёкший назначенный день становится пропущенным и не переносится.

«Запустить/Остановить» управляет работой сейчас. «Автозапуск после рестарта» задаёт состояние после нового запуска процесса. Ручной стоп сохраняется. Остановка не допускает новую отправку; уже начатый запрос может завершиться в течение ограниченного времени. Если запрос принудительно отменён и факт доставки неизвестен, слот получает `unknown` и не повторяется автоматически.

Перед вызовом PyMax создаётся долговечная операция. «Принято» устанавливается только при наличии ID ответа. Только доказанный отказ до отправки допускает до трёх настоящих попыток подключения/отправки с паузами 5/15 секунд. Таймаут и любой неопределённый ответ требуют ручной сверки. После рестарта `in_flight` становится `unknown`.

## Тексты и настройки

Общий пул поддерживает редактирование и импорт TXT. Версия пула содержит сохраняемую перемешанную очередь без повтора до её исчерпания. Обновление создаёт новую версию; подготовленный слот сохраняет свой текст.

Настройки: часовой пояс, окна будней `09:00–13:00, 16:00–21:00`, окна выходных `11:00–14:00, 17:00–20:00`, пауза `5–15` секунд и автозапуск. Дневные лимиты, разогрев, искусственная активность и ручная внеплановая отправка отсутствуют.

## Архитектура и безопасность

Один Python 3.12/FastAPI-процесс, одна SQLite с WAL, Docker Compose, Caddy HTTPS, обычный JavaScript. PyMax закреплён на 2.4.1 и вызывается через единственный адаптер. PostgreSQL, Redis, Celery и frontend-фреймворки не используются. Сессии PyMax хранятся в зашифрованных файлах; временная SQLite-копия находится в tmpfs.

База хранит группы, аккаунты, прокси/назначения, гостевые ссылки и попытки, версии пула, слоты, операции, журнал и настройки. Обновление схемы должно быть повторяемым и не удалять пользовательские строки. Проект не требует отдельного файла разрешения MAX или ссылки на договор. Секреты и номера не выводятся в UI и журнал; неопределённые отправки не повторяются автоматически.

## Приёмочные проверки

Проверяются: 10 групп / 100 аккаунтов; последовательные отправки внутри группы и параллелизм между группами; недельный лимит; сохранение дня, назначения прокси и текста слота; пропуск истёкшего дня; `unknown`; цикл сообщений; гостевое подключение и восстановление после обновления; истёкшая, отозванная и исчерпанная ссылка; ошибка прокси; резервное копирование и восстановление.

UI проверяется на 390, 768 и 1440 px, с клавиатурой, длинными значениями и состояниями ошибок. Все автоматические тесты используют фиктивный PyMax и отдельную SQLite; они не подтверждают фактическую доставку SMS/MAX.
