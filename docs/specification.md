# Техническая спецификация MAXBOT v2

## Назначение и пользователи

Однопользовательская приватная панель для недельного расписания MAX-сообщений. Логин владельца задаётся установкой (`edifier8989` по умолчанию), хеш пароля — через интерактивный хешер. Форма входа не содержит предзаполненных учётных данных и просит браузер не выполнять автозаполнение. Пароль хранится как bcrypt-хеш; cookie — HttpOnly/Secure/SameSite Strict; изменения требуют CSRF-токен и проверку Origin. Регистрации, роли, организации и подписки отсутствуют.

## Группы, аккаунты и подключения

Группа содержит имя, MAX invite link, закреплённый chat ID и статус. MAX-аккаунт принадлежит одной группе и имеет постоянное назначение IP VDS. При создании группы автоматически выдаётся гостевая ссылка на 7 дней без ограничения подключений; повторное открытие сохраняет её, замена и отзыв остаются явными действиями. Гость указывает ФИО и российский телефон, вводит OTP и, если потребуется, облачный пароль MAX. После входа приложение вступает по сохранённой ссылке и подтверждает членство. Если вступление не удалось, вход сохраняется, аккаунт остаётся в `needs_membership`, а гость может вступить вручную и повторить проверку; до членства отправка заблокирована.

Первый успешно авторизованный номер задаёт chat ID группы через PyMax; следующие должны подтвердить ту же группу. Ответ о вступлении в другой chat ID не принимается; при неопределённом результате членство проверяется чтением, без повтора вступления. Успех показывается только после подтверждения членства и сохранения зашифрованной сессии. Смена MAX invite link отзывает гостевую ссылку, отменяет незавершённые подключения и сбрасывает chat ID до новой проверки. Сессия подключения живёт до 15 минут; после перезагрузки браузер восстанавливает шаг по ID попытки из `sessionStorage`. Код и пароль там не хранятся. Просроченные попытки завершаются до нового запуска и не занимают лимит приглашения. Старый единственный `pending`-аккаунт с эквивалентным номером переиспользуется; конфликтующие записи не объединяются.

Сервер принимает `+7XXXXXXXXXX`, `7XXXXXXXXXX`, `8XXXXXXXXXX` и 10 цифр, а также пробелы, скобки и дефисы. Буквы, другая длина и иной международный префикс отклоняются. До поиска и записи аккаунта номер приводится к `+7XXXXXXXXXX`; ошибочные старые `+8…` учитываются при поиске, но не являются допустимым новым вводом. Полный номер отсутствует в списковом API и карточке владельца.

## Исходящие IP VDS

Общий пул `server_ips` хранит публичные IPv4 VDS и состояния `enabled`/`available`; `ip_assignments` закрепляет один IP за аккаунтом. Новый адрес после обнаружения и проверки исходящего соединения остаётся выключенным до ручного включения. Новому аккаунту выбирается включённый адрес с наименьшим числом назначений, при равенстве — меньший ID. `62.109.10.109` исключён из MAX-соединений, начальный адрес — `62.109.20.186`. При миграции существующих аккаунтов назначение создаётся повторяемо без изменения сессий и истории. Таблицы прокси сохраняются как исторические данные.

Вход использует один PyMax-клиент со стандартным `SmsAuthFlow` и веб-провайдерами OTP/2FA. Адаптер привязывает TCP-соединения к назначенному IP; этот же адрес применяется к запросу кода, проверке OTP/пароля, членству и отправке. Отсутствующий, отключённый или недоступный IP блокирует действие без автоматического обхода. Ответ `request_code` не означает доставку кода. `error.profile.active.session.no2fa` выводится как ограничение MAX после OTP: аккаунт сохраняется для повторной попытки после установки пароля, код автоматически не запрашивается.

## Расписание и отправки

Перед каждой попыткой отправки повторно проверяются назначение, включённость, доступность и фактическое наличие исходящего IP; изменение останавливает работу со старым подключением. Остальные правила расписания и отправки не менялись.

Неделя — понедельник–воскресенье в настраиваемой тайм-зоне (по умолчанию `Europe/Moscow`). День назначается один раз по наименьшей загрузке. Максимум — одно подтверждённое MAX-сообщение на аккаунт за неделю. На группу запускается одна последовательная worker-задача; разные группы могут работать параллельно. Истёкший назначенный день становится пропущенным и не переносится.

«Запустить/Остановить» управляет работой сейчас. «Автозапуск после рестарта» задаёт состояние после нового запуска процесса. Ручной стоп сохраняется. Остановка не допускает новую отправку; уже начатый запрос может завершиться в течение ограниченного времени. Если запрос принудительно отменён и факт доставки неизвестен, слот получает `unknown` и не повторяется автоматически.

Перед вызовом PyMax создаётся долговечная операция. «Принято» устанавливается только при наличии ID ответа. Только доказанный отказ до отправки допускает до трёх настоящих попыток подключения/отправки с паузами 5/15 секунд. Таймаут и любой неопределённый ответ требуют ручной сверки. После рестарта `in_flight` становится `unknown`.

## Тексты и настройки

Общий пул поддерживает редактирование и импорт TXT. Версия пула содержит сохраняемую перемешанную очередь без повтора до её исчерпания. Обновление создаёт новую версию; подготовленный слот сохраняет свой текст.

Настройки: часовой пояс, окна будней `09:00–13:00, 16:00–21:00`, окна выходных `11:00–14:00, 17:00–20:00`, пауза `5–15` секунд и автозапуск. Дневные лимиты, разогрев, искусственная активность и ручная внеплановая отправка отсутствуют.

## Архитектура и безопасность

Имена зашифрованных файлов с `session_generation > 0` читаются без переименования и удаления; для старой схемы столбец добавляется повторяемой миграцией со значением 0. Если создание PyMax-клиента с уже открытой сессией завершается ошибкой, временная расшифрованная копия удаляется. API валидации возвращает безопасный код ошибки без исходного ввода. Сырые сообщения и логи PyMax не выводятся в обычные журналы.

Один Python 3.12/FastAPI-процесс, одна SQLite с WAL, Docker Compose в сети хоста, Caddy HTTPS, обычный JavaScript. Приложение слушает только `127.0.0.1:8000`, Caddy — 80/443. PyMax закреплён на 2.4.1 и вызывается через единственный адаптер. PostgreSQL, Redis, Celery и frontend-фреймворки не используются. Сессии PyMax хранятся в зашифрованных файлах; временная SQLite-копия находится в tmpfs.

База хранит группы, аккаунты, IP/назначения, исторические прокси/назначения, гостевые ссылки и попытки, версии пула, слоты, операции, журнал и настройки. Обновление схемы должно быть повторяемым и не удалять пользовательские строки. Проект не требует отдельного файла разрешения MAX или ссылки на договор. Секреты и номера не выводятся в UI и журнал; неопределённые отправки не повторяются автоматически.

## Приёмочные проверки

Проверяются: 10 групп / 100 аккаунтов; последовательные отправки внутри группы и параллелизм между группами; недельный лимит; сохранение дня, назначения IP и текста слота; пропуск истёкшего дня; `unknown`; цикл сообщений; гостевое подключение и восстановление после обновления; истёкшая, отозванная и исчерпанная ссылка; исчезновение IP; резервное копирование и восстановление.

UI проверяется на 390, 768 и 1440 px, с клавиатурой, длинными значениями и состояниями ошибок. Все автоматические тесты используют фиктивный PyMax и отдельную SQLite; они не подтверждают фактическую доставку SMS/MAX.
