# Техническая спецификация MAXBOT v2

## Назначение и пользователи

Однопользовательская приватная панель для недельного расписания MAX-сообщений. Логин владельца задаётся установкой (`edifier8989` по умолчанию), хеш пароля — через интерактивный хешер. Форма входа не содержит предзаполненных учётных данных и просит браузер не выполнять автозаполнение. Пароль хранится как bcrypt-хеш; cookie — HttpOnly/Secure/SameSite Strict; изменения требуют CSRF-токен и проверку Origin. Регистрации, роли, организации и подписки отсутствуют.

## Группы, аккаунты и подключения

Группа содержит имя, MAX invite link, закреплённый chat ID и статус. MAX-аккаунт принадлежит одной группе и имеет постоянное назначение IP VDS. При создании группы автоматически выдаётся гостевая ссылка на 7 дней без ограничения подключений; повторное открытие сохраняет её, замена и отзыв остаются явными действиями. Открытие ссылки не обращается к MAX и не выбирает IP. После нажатия кнопки подключения сервер в одной SQLite-транзакции закрепляет наименее загруженный включённый и доступный IP, прежде чем запросить код. Пока попытка выполняется, адрес не меняется. Гость указывает ФИО и российский телефон, вводит OTP и, если MAX прислал challenge, облачный пароль. После входа приложение проверяет профиль и надёжно сохраняет сессию, затем вступает по сохранённой ссылке и подтверждает членство. `auth_state` отдельно хранит `unverified`, `authenticated` или `reauth_required`; статус членства остаётся в `accounts.status`. Если вступление не удалось, авторизация сохраняется, аккаунт остаётся в `needs_membership`, а гость может вступить вручную и повторить проверку. Живая попытка сохраняет телефон до подтверждения членства, поскольку он нужен для открытия PyMax-сессии; после завершения попытки ФИО и телефон очищаются. Это состояние переживает рестарт приложения и действует до отзыва или истечения гостевой ссылки; после этого гость получает указание обратиться к владельцу без предложения повторить вход. До членства отправка заблокирована. Явный отказ MAX сохранённого токена в гостевом входе, проверке членства или назначения блокирует дальнейшее использование этого аккаунта; владелец может вручную переподключить номер в той же группе.

Первый успешно авторизованный номер задаёт chat ID группы через PyMax; следующие должны подтвердить ту же группу. Ответ о вступлении в другой chat ID не принимается; при неопределённом результате членство проверяется чтением, без повтора вступления. Страница подтверждает подключение только после членства и сохранения сессии. При challenge MAX состояние меняется на `verifying_password` сразу после принятия ввода; повторная отправка блокируется до следующего запроса провайдера. Каждый повторный запрос пароля показывает, что MAX отклонил предыдущий. Смена MAX invite link отзывает гостевую ссылку, отменяет незавершённые подключения и сбрасывает chat ID до новой проверки. Auth-попытка живёт до 15 минут; после перезагрузки браузер восстанавливает её по ID из `sessionStorage`, где не хранятся OTP и пароль. Просроченные попытки авторизации завершаются до проверки лимита приглашения. `waiting_membership` сохраняется до окончания приглашения. Старый `pending`-аккаунт с эквивалентным номером переиспользуется; аккаунт с `reauth_required` можно вручную переподключить в исходной группе даже после отказа сохранённой сессии, с новым поколением и без освобождения/смены IP; его прежняя ожидающая проверка членства отменяется. Конфликтующие записи не объединяются.

Сервер принимает `+7XXXXXXXXXX`, `7XXXXXXXXXX`, `8XXXXXXXXXX` и 10 цифр, а также пробелы, скобки и дефисы. Буквы, другая длина и иной международный префикс отклоняются. До поиска и записи аккаунта номер приводится к `+7XXXXXXXXXX`; ошибочные старые `+8…` учитываются при поиске, но не являются допустимым новым вводом. Полный номер отсутствует в списковом API и карточке владельца.

## Исходящие IP VDS

Общий пул `server_ips` хранит публичные IPv4 VDS и состояния `enabled`/`available`; `ip_assignments` закрепляет один IP за аккаунтом. Новый адрес после обнаружения и проверки исходящего соединения остаётся выключенным до ручного включения владельцем. Новый аккаунт получает включённый IP с наименьшей расчётной нагрузкой: уникальные авторизованные аккаунты плюс уникальные действующие попытки входа. При равной нагрузке выбирается IP с самым старым `last_assigned_at`, затем меньший ID; отметка времени записывается вместе с назначением. Исторические ошибки и неподтверждённые назначения не влияют на балансировку. Повтор активного номера сохраняет его прежний IP, а после окончательной неудачи новое ручное добавление получает новый аккаунт и балансируется как новая попытка. API отдельно возвращает `assigned_count`, `authenticated_count`, `in_progress_count` и `unconfirmed_count`; все счётчики считают уникальные неудалённые аккаунты. `62.109.10.109` исключён из MAX-соединений, начальный адрес — `62.109.20.186`. При миграции существующих аккаунтов назначение создаётся повторяемо без изменения сессий и истории. Таблицы прокси сохраняются как исторические данные.

Вход использует один PyMax-клиент со стандартным `SmsAuthFlow` и веб-провайдерами OTP/2FA. Адаптер привязывает TCP-соединение к назначенному IP и проверяет актуальность назначения перед открытием сокета и каждой отправкой кадра. Диагностика фиксирует безопасные этапы соединения, handshake, запроса кода, OTP, 2FA, login и операций членства: время, наличие ответа и класс исключения; сырые кадры и данные ответа не сохраняются. Отсутствующий, отключённый, исчезнувший или переназначенный IP завершает попытку; перехода на другой адрес и автоматического повтора `request_code` нет. Журнал различает ответ MAX на запрос кода, ожидание ввода OTP и сетевую ошибку, но не объявляет SMS доставленной без подтверждения пользователя. Для неподтверждённого нового аккаунта `error.profile.active.session.no2fa` и любая другая окончательная ошибка закрывает клиент и очищает сессию/назначение; ранее успешно авторизованный аккаунт сохраняется для ручного повтора без автоматического нового запроса кода.

## Расписание и отправки

Перед каждой попыткой отправки повторно проверяются назначение, включённость, доступность и фактическое наличие исходящего IP; изменение останавливает работу со старым подключением. Остальные правила расписания и отправки не менялись.

Неделя — понедельник–воскресенье в настраиваемой тайм-зоне (по умолчанию `Europe/Moscow`). День назначается один раз по наименьшей загрузке. Максимум — одно подтверждённое MAX-сообщение на аккаунт за неделю. На группу запускается одна последовательная worker-задача; разные группы могут работать параллельно. Истёкший назначенный день становится пропущенным и не переносится.

«Запустить/Остановить» управляет работой сейчас. «Автозапуск после рестарта» задаёт состояние после нового запуска процесса. Ручной стоп сохраняется. Остановка не допускает новую отправку; уже начатый запрос может завершиться в течение ограниченного времени. Если запрос принудительно отменён и факт доставки неизвестен, слот получает `unknown` и не повторяется автоматически.

В списке номеров текст ошибки недельного слота выводится только при непустом `error_code`; запланированный слот без кода ошибки не сопровождается общим предупреждением. Ошибки подключения отображаются отдельно от ошибок слота.

Перед вызовом PyMax создаётся долговечная операция. «Принято» устанавливается только при наличии ID ответа. Только доказанный отказ до отправки допускает до трёх настоящих попыток подключения/отправки с паузами 5/15 секунд. Таймаут и любой неопределённый ответ требуют ручной сверки. После рестарта `in_flight` становится `unknown`.

## Тексты и настройки

Общий пул поддерживает редактирование и импорт TXT. Версия пула содержит сохраняемую перемешанную очередь без повтора до её исчерпания. Обновление создаёт новую версию; подготовленный слот сохраняет свой текст.

Настройки: часовой пояс, окна будней `09:00–13:00, 16:00–21:00`, окна выходных `11:00–14:00, 17:00–20:00`, пауза `5–15` секунд и автозапуск. Дневные лимиты, разогрев, искусственная активность и ручная внеплановая отправка отсутствуют.

## Архитектура и безопасность

`auth_state` добавляется повторяемой миграцией. Только при первом добавлении старые `active` и `needs_membership` переносятся в `authenticated`; остальные аккаунты остаются `unverified`. Наличие файла или токена само по себе не доказывает вход. Имена файлов с `session_generation > 0` сохраняются без переименования и удаления; при явном отказе PyMax `FAIL_LOGIN_TOKEN`/`FAIL_LOGOUT_ALL` аккаунт получает `reauth_required`, и следующий ручной запуск использует новое поколение, оставляя прежний файл и IP на месте. Это применяется также к уже активному аккаунту: отправки для него блокируются до ручного входа. Если его старая сессия ожидала подтверждения членства, эта попытка отменяется; при лимитированной ссылке её использование переходит новой попытке того же номера. Снимок PyMax создаётся через SQLite backup, шифруется и атомарно заменяет текущую генерацию; plaintext-копия остаётся доступна живому клиенту до его закрытия. База без токена не создаёт новый постоянный файл и не заменяет старый. API валидации возвращает безопасный код ошибки без исходного ввода. Сырые сообщения и логи PyMax не выводятся в обычные журналы.

Один Python 3.12/FastAPI-процесс, одна SQLite с WAL, Docker Compose в сети хоста, Caddy HTTPS, обычный JavaScript. Приложение слушает только `127.0.0.1:8000`, Caddy — 80/443. PyMax закреплён на 2.4.1 и вызывается через единственный адаптер. PostgreSQL, Redis, Celery и frontend-фреймворки не используются. Сессии PyMax хранятся в зашифрованных файлах; временная SQLite-копия находится в tmpfs.

База хранит группы, аккаунты, IP/назначения, исторические прокси/назначения, гостевые ссылки и попытки, версии пула, слоты, операции, безопасный журнал событий и настройки. Завершённые попытки не хранят телефон/ФИО. Поле `ever_authenticated` защищает старый успешно вошедший аккаунт от автоочистки при ошибке переподключения. Удаление владельцем требует CSRF, ждёт завершения/закрытия клиента и удаляет все поколения сессии и временные SQLite для точного ID аккаунта; таблицы отправок, операций, слотов, аккаунт-ID и обезличенные события остаются. Телефон заменяется маркером, IP освобождается, а нормализованный номер сохраняется только как HMAC для недельного лимита после новой регистрации. При незавершённой очистке аккаунт заблокирован в `delete_pending`, повтор удаления и восстановление после рестарта продолжают операцию; ошибка файловой системы не считается успехом. При отправке `in_flight` или `unknown` удаление возвращает 409 до начала изменений и требует ручной сверки.

Для существующих неподтверждённых записей `python -m scripts.cleanup_unverified_accounts` строит отдельный dry-run отчёт только по ID. Применение разрешено лишь для переданного вручную списка просмотренных ID; перед изменением скрипт снова проверяет каждый аккаунт и возвращает ненулевой код при частичном выполнении. Живые, неоднозначные и завершённые успешные попытки, runtime-каталоги, история слотов/отправок/операций, авторизационные маркеры, токенизированные и нечитаемые поколения сессий исключаются. Старый `+8` приводится к `+7` перед HMAC; ненормализуемая запись без истории отправок обезличивается без отпечатка. Миграции повторяемы и не удаляют данные. Проект не требует отдельного файла разрешения MAX или ссылки на договор. Секреты, телефоны, OTP и токены не выводятся в UI и журнал; неопределённые отправки не повторяются автоматически.

## Приёмочные проверки

Проверяются: конкурентное назначение и чередование IP при равной нагрузке; освобождение адреса и отсутствие смены IP внутри попытки; очистка новой неавторизованной попытки и её восстановление после рестарта; сохранение успешного входа при ошибке членства и очистка PII после членства; повторный вход старого аккаунта; удаление всех поколений, повтор DELETE и отказ файловой системы; конфликты с `in_flight`/`unknown`; недельный лимит по HMAC после повторной регистрации; сохранение операций/слотов; существующие проверки расписания и отправки.

UI проверяется на 390, 768 и 1440 px, с клавиатурой, длинными значениями и состояниями ошибок. Все автоматические тесты используют фиктивный PyMax и отдельную SQLite; они не подтверждают фактическую доставку SMS/MAX.
