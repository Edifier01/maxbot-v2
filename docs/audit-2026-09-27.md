# Аудит авторизации и сессий MAXBOT v2

Дата: 2026-09-27. Изменения подготовлены в `codex/auth-session-lifecycle`; VDS, производственная SQLite и production session files в рамках этой работы не открывались и не менялись.

## Проверенная последовательность PyMax

Установленная зависимость — `maxapi-python==2.4.1`. Проект создаёт один `Client` через `maxbot_v2/max_adapter.py` со штатным `SmsAuthFlow`: запрос кода, ввод OTP, `send_code`, пароль только по challenge MAX и дальнейший `Client.connect()`. Это совпадает с [исходником SMS flow v2.4.1](https://github.com/MaxApiTeam/PyMax/blob/v2.4.1/src/pymax/auth/sms.py) и [порядком входа и сохранения токена в PyMax](https://github.com/MaxApiTeam/PyMax/blob/v2.4.1/src/pymax/app.py). Интеграция оставляет один клиент и стандартный flow; к нему добавлены шифрование сессии, безопасные таймауты и закрепление каждого TCP-соединения за выбранным IPv4.

Ранее транспорт проверял назначение IP в основном вокруг `connect()`. Теперь callback адаптера проверяет актуальность закрепления до открытия сокета и перед каждой отправкой TCP-кадра. Если IP исчез, выключен или переназначен, текущий запрос прекращается; автоматического перехода на другой IP и повтора неопределённого `request_code` нет.

## Сессии и повтор входа

PyMax создаёт SQLite-файл до успешного входа, поэтому сам файл не доказывает наличие авторизованной сессии. Раньше `seal()` безусловно сохранял зашифрованную копию даже при пустой таблице токенов. Теперь снимок делается только из согласованной SQLite-копии через backup API и только при наличии токена; зашифрованный файл атомарно заменяется. Пустая БД не создаёт новое постоянное поколение и не перезаписывает старую сессию. Рабочая БД остаётся доступна клиенту до закрытия.

PyMax 2.4.1 сохраняет auth token до полного завершения `login()`. Если MAX явно отвечает `FAIL_LOGIN_TOKEN` или `FAIL_LOGOUT_ALL`, аккаунт получает `reauth_required`, в том числе если отказ произошёл при восстановлении членства или подключении активного аккаунта к проверке/отправке. Отправки этого аккаунта блокируются до ручного входа. Следующий ручной запуск в исходной группе увеличивает `session_generation`, сохраняя прежние session files, аккаунт и назначение IP; старое ожидающее членство отменяется. Если оно занимало единственное использование той же гостевой ссылки, повторный вход переиспользует этот слот. Сетевой timeout или другой неопределённый результат сам по себе не меняет поколение.

Добавлена повторяемая миграция `accounts.auth_state`: только при первом добавлении столбца прежние статусы `active` и `needs_membership` переносятся в `authenticated`; остальные аккаунты остаются `unverified`. Наличие токена или файла не повышает статус авторизации. Членство и успешный вход остаются разными состояниями.

## OTP, 2FA и восстановление членства

После принятия OTP/пароля API немедленно переводит попытку в `verifying_code`/`verifying_password` и отклоняет повторную отправку, пока PyMax не запросит следующий ввод. Таймаут ввода OTP или пароля отделён от сетевого таймаута. Challenge 2FA обрабатывается штатным PyMax flow: отказ пароля запрашивает пароль ещё раз, но не вызывает повторный OTP; предел PyMax — пять проверок. `error.profile.active.session.no2fa` остаётся отказом MAX без автоматического обхода.

`waiting_membership` продлевается до срока гостевой ссылки и исключён из отмены при рестарте и очистки просроченных OTP/2FA-попыток. После отзыва или истечения приглашения состояние становится терминальным и сообщает гостю обратиться к владельцу, не предлагая новый вход. Перед проверкой лимита использования ссылки старые auth-попытки завершаются.

## Назначения IP и счётчики

Назначение IP сохраняется даже для неудачной попытки и отображается как `assigned_count`. Дополнительно API возвращает количество авторизованных аккаунтов, текущих попыток и остальных неподтверждённых назначений; все показатели считают уникальные аккаунты. Новое распределение IP учитывает только авторизованные номера плюс действующие попытки. Ошибочные исторические назначения не создают искусственную нагрузку. Повтор одного номера использует тот же аккаунт и IP.

## Проверки и ограничения

Автотесты используют отдельную SQLite и фиктивный PyMax; они проверяют миграцию, снимки и сохранность поколений, маршрут IP перед отправками, повтор 2FA, лимиты пароля, повтор номера, счётчики, истечение приглашения и восстановление `waiting_membership`. Браузерные тесты работают в Chromium на существующих ширинах 390, 768 и 1440 px.

Эти тесты не подтверждают доставку SMS, вход на реальный MAX, доступность production IP или отправку сообщений. Реальные производственные сессии не инвентаризировались: какие из них пустые, содержат отклонённый токен или относятся к старым поколениям, пока неизвестно. Последняя записанная в [состоянии проекта](project-state.md) установленная ревизия VDS — `95c7072f49db1c3d0e86bfab87dc481eaaf79b64`; в рамках этого PR её не сверяли и не меняли.

Фактические команды и результаты проверок перечислены в [журнале изменений](change-log.md). PyMax-версия, архитектура и пользовательские SQLite/session files сохраняются; production проверка и выпуск требуют отдельного этапа с резервной копией и проверкой восстановления.
