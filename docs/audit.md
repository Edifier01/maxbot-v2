# Аудит исходного MAXBOT

> Исторический аудит архитектуры `maxbot-main` перед началом v2. Он описывает перенос старого приложения в v2 и не заменяет актуальные инструкции/состояние проекта. Пользовательские данные уже существующей v2 сохраняются.

Аудит основан на исходниках в `maxbot-main`, его README, Docker Compose, репозитории расписания и worker, а также имеющемся историческом аудите `docs/audit/PROJECT-AUDIT-2026-09-24.md`.

## Текущее устройство

- FastAPI-приложение построено для нескольких организаций. PostgreSQL хранит пользователей и подписки, SQLite обслуживает рассылки, Redis/Celery — фоновые и дополнительные сценарии.
- Недельное расписание уже привязано к MAX-аккаунту. День распределяется по наименьшей загрузке и сохраняется; прокси также постоянно назначается из группы по наименьшей загрузке.
- В старой реализации работает общий worker. Если у одного аккаунта несколько групп, фактическая обработка не соответствует модели «один номер — одна группа».
- Тексты лежат в общей библиотеке с версиями, но недельный слот выбирает случайный текст и не гарантирует цикл без повтора.
- Подключение по гостевой ссылке и ручное вступление в группу уже предусмотрены. Создание ссылки пока зависит от ручного подтверждения chat ID.
- Существующие защищённые сессии, журнал отправки и поведение без автоповтора при неизвестном исходе важны как требования надёжности.
- Локальный набор проверок исходного проекта на момент аудита прошёл 752 теста; ещё 20 были пропущены. Это не подтверждает готовность новой реализации. Переданный каталог исходного проекта не содержит Git-метаданных, поэтому аудит не привязан к commit SHA.

## Решения для v2

Оставить один FastAPI-процесс и SQLite в WAL; исключить PostgreSQL, Redis, Celery, роли, регистрации, организации и подписки. Закрепить ровно одну группу и прокси за номером, дать каждой группе последовательную задачу, а разные группы запускать параллельно. Сохранить распределение дня/прокси по наименьшей загрузке и заменить случайный выбор текста сохраняемой перемешанной очередью.

При первоначальном переносе из старого `maxbot-main` данные не импортировались. Это историческое решение не является указанием удалять группы, прокси, аккаунты или сессии из используемой установки v2. Исторические результаты тестов исходного проекта не считать приёмкой v2.

## PyMax

В исходном проекте закреплена `maxapi-python==2.4.1`. Документация PyMax подтверждает TCP `Client`, одноразовый жизненный цикл `connect()` / `close()`, `ExtraConfig.proxy`, `persist_session`, `resolve_group_by_link`, `get_chat()` и `send_message(chat_id=..., text=...)`. Приложение v2 держит все вызовы за единственным адаптером и требует ID ответа для статуса «принято». PyMax работает через неофициальный API MAX; реальная совместимость подтверждается только контролируемым запуском, а не фиктивными тестами.
