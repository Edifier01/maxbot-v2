# Состояние проекта

Обновлено: 2026-09-27. Текущее устройство и известные ограничения собраны здесь, чтобы следующий агент не восстанавливал их по истории переписки.

## Устройство

- Python 3.12, FastAPI, SQLite/WAL, обычный JavaScript.
- Один PyMax-адаптер (`maxbot_v2/max_adapter.py`), версия `maxapi-python==2.4.1`.
- Один процесс планировщика/worker manager; параллелизм между группами и последовательность внутри группы.
- Docker Compose и Caddy. Внешний порт приложения не опубликован; сессии PyMax хранятся отдельными зашифрованными файлами, временная SQLite-копия — в tmpfs.
- Проект рассчитан на сохранение используемой SQLite и session files. Перед выпуском нужно снять резервную копию и проверить восстановление.

## Основные сценарии

1. Владелец создаёт группу: гостевая ссылка на 7 дней без лимита подключений появляется автоматически. Владелец добавляет прокси группы.
2. Гость вводит ФИО и российский номер (сервер приводит его к `+7XXXXXXXXXX`), затем OTP/облачный пароль. После входа панель пытается вступить в MAX-группу по сохранённой ссылке и подтверждает членство.
3. При неудаче вступления сессия сохраняется, аккаунт остаётся в `needs_membership`; владелец или гость проверяет членство после ручного вступления. Отправка допускается только из `active`.
   Кнопка отмены после сохранения входа не показывается. При новом подключении просроченная ожидающая OTP/пароль задача отменяется, чтобы освободить блокировку аккаунта.
4. Worker отправляет сообщение в установленный день и временное окно. Каждая отправка хранится в журнале операций; неизвестный результат требует ручной сверки.
5. Ручной «Стоп» останавливает текущую работу. Флажок автозапуска задаёт состояние только после перезапуска процесса.

## Безопасные эксплуатационные ограничения

- Для гостевой авторизации разрешён прямой только один вызов `request_code`; до него проверяются назначение включённого прокси и расшифровка его URL. Проверка кода, 2FA, вход, членство и все остальные обращения идут через назначенный прокси; автоматического обхода ошибок прокси нет.
- `request_code` выполняется отдельным временным PyMax-клиентом с `proxy=None` и `persist_session=False`. Ответ для OTP-челленджа остаётся в памяти процесса; основная авторизация и зашифрованное сохранение сессии идут через адаптер с назначенным прокси.
- Для одноразовой диагностики адаптер может удержать этот временный клиент открытым до сигнала `hold_open_until`; обычный путь панели событие не передаёт. Диагностический вызов не проверяет OTP и не создаёт сессию.
- Успешный ответ на `request_code` означает принятие запроса MAX, но не подтверждает доставку SMS.
- UI тестируется на 390, 768 и 1440 px. Автоматические проверки используют отдельную SQLite и фиктивный PyMax; реальные SMS, прокси и отправки в них не проверяются.
- На старте `/health` отдаёт `revision`. `unknown` означает, что сборка не получила SHA.
- Схема добавляет `session_generation` повторяемо; файлы обоих поколений открываются по их существующим именам. Полный телефон не выдаётся списковым API. Ошибки валидации не отражают исходный ввод, а сырые сообщения PyMax подавлены на границе адаптера.
- После получения блокировки и до сетевых действий приложение перепроверяет назначенный прокси; во время отправки также сравнивает его зашифрованный адрес. Уже начатый сетевой запрос нельзя отменить задним числом, поэтому окончательный результат подтверждается отдельной проверкой.

## Выпуск 2026-09-27

После слияния PR #11 GitHub и локальный `main` совпали на `559536dc0466b438e70835d02d28bd9dccc95eeb`. Владелец обновил VDS до этого SHA. Перед сборкой командный блок проверил чистый checkout и `global_stop=1`, прежний образ помечен для отката как `maxbot-app:rollback-fc74ce6`. По прямому указанию владельца свежий архив SQLite и сессий не создавался; ранее подтверждённая им внешняя копия осталась прежней точкой восстановления и не содержит последующих изменений данных. Вывод владельца `docker compose ps` показал здоровый `app`, работающий Caddy и только внутренний порт приложения; его HTTPS `/health` вернул `{"status":"ok","revision":"559536dc0466b438e70835d02d28bd9dccc95eeb"}`. Независимая проверка URL агентом была заблокирована средой. Отправки остаются остановленными; реальная доставка OTP, вход, вступление и сохранение новой сессии не подтверждены.

На этом выпуске владелец выполнил одну гостевую и одну отдельную прямую диагностическую попытку для тестового аккаунта. Обе получили ответ MAX с токеном, шестизначным кодом и `request_count_left=10`, но код не пришёл; гостевая попытка отменена штатно. Отдельная попытка не открывала основной клиент через прокси. Эти результаты исключают его одновременное соединение как необходимое условие сбоя, но не различают IP VDS и немедленное закрытие временного клиента. Ручная проверка с удержанием прямого соединения ещё не проведена.

PR #9 слит, GitHub и локальный `main` совпали на `fc74ce61c6a6f3ca772e9197bc0817a8b869fe11`. Владелец собрал и запустил этот SHA на VDS.
