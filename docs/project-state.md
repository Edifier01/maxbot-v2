# Состояние проекта

Обновлено: 2026-09-25. Текущее устройство и известные ограничения собраны здесь, чтобы следующий агент не восстанавливал их по истории переписки.

## Устройство

- Python 3.12, FastAPI, SQLite/WAL, обычный JavaScript.
- Один PyMax-адаптер (`maxbot_v2/max_adapter.py`), версия `maxapi-python==2.4.1`.
- Один процесс планировщика/worker manager; параллелизм между группами и последовательность внутри группы.
- Docker Compose и Caddy. Внешний порт приложения не опубликован; сессии PyMax хранятся отдельными зашифрованными файлами, временная SQLite-копия — в tmpfs.
- Проект рассчитан на сохранение используемой SQLite и session files. Перед выпуском нужно снять резервную копию и проверить восстановление.

## Основные сценарии

1. Владелец создаёт группу и её прокси, затем выдаёт гостевую ссылку.
2. Гость запрашивает SMS-код, вводит OTP/облачный пароль и самостоятельно вступает в MAX-группу.
3. Панель проверяет членство через PyMax. Состояния `active` и `needs_membership` допускают повторную проверку.
4. Worker отправляет сообщение в установленный день и временное окно. Каждая отправка хранится в журнале операций; неизвестный результат требует ручной сверки.
5. Ручной «Стоп» останавливает текущую работу. Флажок автозапуска задаёт состояние только после перезапуска процесса.

## Безопасные эксплуатационные ограничения

- Все обращения к MAX идут через назначенный прокси; автоматического прямого обхода прокси нет.
- Успешный ответ на `request_code` означает принятие запроса MAX, но не подтверждает доставку SMS.
- UI тестируется на 390, 768 и 1440 px. Автоматические проверки используют отдельную SQLite и фиктивный PyMax; реальные SMS, прокси и отправки в них не проверяются.
- На старте `/health` отдаёт `revision`. `unknown` означает, что сборка не получила SHA.
