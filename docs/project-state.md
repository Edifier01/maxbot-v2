## Устройство

- Python 3.12, FastAPI, SQLite/WAL, обычный JavaScript.
- Один PyMax-адаптер (`maxbot_v2/max_adapter.py`), версия `maxapi-python==2.4.1`.
- Один процесс планировщика/worker manager; параллелизм между группами и последовательность внутри группы.
- Docker Compose в сети хоста и Caddy на 80/443. Приложение слушает только `127.0.0.1:8000`; сессии PyMax хранятся отдельными зашифрованными файлами, временная SQLite-копия — в tmpfs.

## Основные сценарии

1. Владелец создаёт группу: гостевая ссылка на 7 дней без лимита подключений появляется автоматически. Общий пул IP VDS обновляется вручную; новые адреса выключены до включения владельцем.
2. Гость вводит ФИО и российский номер (сервер приводит его к `+7XXXXXXXXXX`), затем OTP/облачный пароль по запросу challenge MAX. Перед отправкой формы OTP/2FA сервер сразу меняет состояние на проверку и блокирует дубль до следующего вызова провайдера.
3. Авторизация подтверждается после успешного профиля PyMax и атомарно сохранённого зашифрованного SQLite-снимка с токеном. `auth_state` отражает `unverified`, `authenticated` или `reauth_required`, а `accounts.status` независимо показывает состояние членства. При неудаче вступления сессия сохраняется, аккаунт остаётся в `needs_membership`; состояние переживает рестарт и 15-минутный срок auth-попытки до окончания или отзыва гостевой ссылки. Отправка допускается только после членства (`active`).
   Кнопка отмены после сохранения входа не показывается. Просроченные ожидающие OTP/пароль задачи завершаются и освобождают блокировку аккаунта; `waiting_membership` не истекает вместе с auth-попыткой.
4. Worker отправляет сообщение в установленный день и временное окно. Каждая отправка хранится в журнале операций; неизвестный результат требует ручной сверки.
5. Ручной «Стоп» останавливает текущую работу. Флажок автозапуска задаёт состояние только после перезапуска процесса.

## Безопасные эксплуатационные ограничения

- Каждый MAX-аккаунт имеет один постоянный исходящий IP VDS. `62.109.10.109` исключён; первым разрешён `62.109.20.186`. Все соединения PyMax, включая запрос кода, OTP/2FA, членство и отправку, привязываются к назначенному адресу; транспорт повторно проверяет назначение перед соединением и каждой отправкой. Смена, отключение или исчезновение адреса останавливает работу без автоматического обхода.
- Вход использует один клиент PyMax 2.4.1 со стандартным `SmsAuthFlow` и провайдерами веб-формы. Новый постоянный файл создаётся только при наличии токена; сохранение выполняется через SQLite backup и атомарную замену зашифрованного снимка, не удаляя открытую временную БД. Наличие файла или токена само по себе не считается доказательством входа. Явный `FAIL_LOGIN_TOKEN`/`FAIL_LOGOUT_ALL` помечает `reauth_required`; следующий ручной вход переключает поколение, сохраняя старый файл и IP. Окончательная ошибка новой неавторизованной попытки, в том числе `error.profile.active.session.no2fa`, закрывает клиент и удаляет её аккаунт/сессию/IP; ранее авторизованный аккаунт защищён `ever_authenticated`.
- IP API оставляет `assigned_count` для существующих назначений и отдельно показывает сохранённые аккаунты, действующие попытки и остальные неподтверждённые назначения. Выбор IP балансирует уникальные авторизованные аккаунты и незавершённые попытки; исторические ошибки не увеличивают нагрузку. Равную нагрузку разрешает наименее недавно назначавшийся IP, отметка времени фиксируется транзакционно. Повтор активного номера сохраняет назначение, а новая регистрация после очистки получает новое.
- Успешный ответ на `request_code` означает принятие запроса MAX, но не подтверждает доставку SMS.
- UI тестируется на 390, 768 и 1440 px. Автоматические проверки используют отдельную SQLite и фиктивный PyMax; реальные SMS, исходящие IP и отправки в них не проверяются.
- На старте `/health` отдаёт `revision`. `unknown` означает, что сборка не получила SHA.
- Схема добавляет `session_generation` повторяемо; файлы обоих поколений открываются по их существующим именам. Полный телефон не выдаётся списковым API. Ошибки валидации не отражают исходный ввод, а сырые сообщения PyMax подавлены на границе адаптера.
- После получения блокировки и до сетевых действий приложение перепроверяет назначенный IP; во время отправки сравнивает его ID и адрес. Уже начатый запрос нельзя отменить задним числом, поэтому неопределённый результат требует ручной сверки.

## Авторизация и сессии — локальная реализация ветки `codex/auth-session-lifecycle`

Добавлена повторяемая миграция `accounts.auth_state`: при первом добавлении только старые `active` и `needs_membership` считаются уже авторизованными; остальные статусы консервативно остаются `unverified`. Пустые временные БД PyMax после запроса OTP больше не сохраняются. Успешный профиль и token-backed снимок фиксируются до вступления в группу. Явный отказ сохранённого токена переводит аккаунт в `reauth_required` в том числе при отправке и проверке группы; отправки блокируются до ручного переподключения. Следующий ручной запуск в той же группе открывает новое поколение сессии, сохраняя прежние поколения и IP. Если отменяется ожидающее членство этого аккаунта, его место в одноразовой ссылке переиспользуется. Сетевые ошибки не сбрасывают сессию.

PR #17 добавил безопасные этапы диагностики PyMax, повторяемое удаление владельцем сессий всех поколений, блокировку при `in_flight`/`unknown`, восстановление `delete_pending` после рестарта, HMAC недельного лимита, UI подтверждения удаления и отдельный dry-run очистки старых ID. Автоматические проверки используют отдельную SQLite и фиктивный PyMax; они не проверяют фактическую доставку OTP/MAX.

На этапе локальной разработки PR #17 не был установлен на VDS; теперь его выпуск и текущая частичная очистка описаны в начале файла. Реальная доставка OTP, вход MAX, повторное открытие сессии, членство и отправка этой версией по-прежнему не подтверждены.

По прямому указанию владельца свежий архив SQLite и сессий не создавался; ранее подтверждённая им внешняя копия осталась прежней точкой восстановления и не содержит последующих изменений данных. Вывод владельца `docker compose ps` показал здоровый `app`, работающий Caddy и только внутренний порт приложения; его HTTPS `/health` вернул `{"status":"ok","revision":"559536dc0466b438e70835d02d28bd9dccc95eeb"}`. Независимая проверка URL агентом была заблокирована средой. Отправки остаются остановленными; реальная доставка OTP, вход, вступление и сохранение новой сессии не подтверждены.

PR #9 слит, GitHub и локальный `main` совпали на `fc74ce61c6a6f3ca772e9197bc0817a8b869fe11`. Владелец собрал и запустил этот SHA на VDS. Сразу после запуска приложение имело `health: starting`, и первый HTTPS-запрос получил 502; повторный запрос владельца вернул `{"status":"ok","revision":"fc74ce61c6a6f3ca772e9197bc0817a8b869fe11"}`. Владелец подтвердил выгрузку архива за пределы VDS со сверкой SHA-256, успешное тестовое восстановление и остановленное состояние отправок. Эти три действия подтверждены сообщением владельца, отдельной проверкой агентом на VDS не подтверждены. Первая попытка гостевого входа дошла до формы кода: MAX вернул ответ на `request_code`, но владелец не получил OTP. Доставка не подтверждена, вход и автоматическое вступление не завершены. Сохранение сессии после перезапуска и отправка MAX для этого выпуска ещё не проверены.
