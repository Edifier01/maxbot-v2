# Состояние проекта

Обновлено: 2026-09-26. Текущее устройство и известные ограничения собраны здесь, чтобы следующий агент не восстанавливал их по истории переписки.

## Устройство

- Python 3.12, FastAPI, SQLite/WAL, обычный JavaScript.
- Один PyMax-адаптер (`maxbot_v2/max_adapter.py`), версия `maxapi-python==2.4.1`.
- Один процесс планировщика/worker manager; параллелизм между группами и последовательность внутри группы.
- Docker Compose и Caddy. Внешний порт приложения не опубликован; сессии PyMax хранятся отдельными зашифрованными файлами, временная SQLite-копия — в tmpfs.
- Проект рассчитан на сохранение используемой SQLite и session files. Перед выпуском нужно снять резервную копию и проверить восстановление.

## Основные сценарии

1. Владелец создаёт группу и её прокси, затем выдаёт гостевую ссылку.
2. Гость запрашивает SMS-код, вводит OTP/облачный пароль; приложение автоматически вступает в MAX-группу по сохранённой ссылке.
3. Панель проверяет членство через PyMax. Если автоматическое вступление не подтверждено, гость может вступить вручную и повторить проверку. Состояния `active` и `needs_membership` допускают повторную проверку.
4. Worker отправляет сообщение в установленный день и временное окно. Каждая отправка хранится в журнале операций; неизвестный результат требует ручной сверки.
5. Ручной «Стоп» останавливает текущую работу. Флажок автозапуска задаёт состояние только после перезапуска процесса.

## Безопасные эксплуатационные ограничения

- Для гостевой авторизации разрешён прямой только один вызов `request_code`; до него проверяются назначение включённого и `healthy` прокси и расшифровка его URL. Состояние прокси повторно проверяется перед сетевыми шагами. Проверка кода, 2FA, вход, членство и все остальные обращения идут через назначенный прокси; автоматического обхода ошибок прокси нет.
- `request_code` выполняется отдельным временным PyMax-клиентом с `proxy=None` и `persist_session=False`. Ответ для OTP-челленджа остаётся в памяти процесса; основная авторизация и зашифрованное сохранение сессии идут через адаптер с назначенным прокси.
- Российский телефон нормализуется в `+7XXXXXXXXXX` перед сохранением и передачей PyMax. После авторизации приложение автоматически вступает в группу по сохранённой MAX-ссылке и подтверждает членство; при неудаче остаётся ручной путь.
- Прокси проверяются на TCP-туннель до PyMax; только `healthy` допускает внешние действия и назначение. Удаление номера мягкое: история и зашифрованная сессия сохраняются, при `in_flight`/`unknown` удаление блокируется. Перед ожиданием сессии аккаунт получает `removing`, чтобы остановить повторное подключение во время удаления. Телефон не показывается в админском списке и подтверждении удаления.
- Успешный ответ на `request_code` означает принятие запроса MAX, но не подтверждает доставку SMS.
- UI тестируется на 390, 768 и 1440 px. Автоматические проверки используют отдельную SQLite и фиктивный PyMax; реальные SMS, прокси и отправки в них не проверяются.
- На старте `/health` отдаёт `revision`. `unknown` означает, что сборка не получила SHA.
