## Авторизация и SMS: что действительно известно

Ваш консольный пример успешно выполнил вход на ПК **без прокси**. В проекте тот же номер проходит через назначенный группе прокси (`maxbot_v2/max_adapter.py:35-47`, `maxbot_v2/app.py:465-502`). Код `WebCodeAuthFlow` вызывает `request_code` → ждёт ввод → `send_code` (`maxbot_v2/onboarding.py:19-26`), как стандартный [SMS flow PyMax v2.4.1](https://github.com/MaxApiTeam/PyMax/blob/v2.4.1/src/pymax/auth/sms.py). `connect()` допустим для разового входа; `start()` в примере дополнительно оставляет клиента слушать события. PyMax сам использует [TCP через прокси из `ExtraConfig`](https://github.com/MaxApiTeam/PyMax/blob/v2.4.1/src/pymax/client.py).

Состояние `waiting_code` означает, что `request_code` **вернул ответ**. Оно не подтверждает доставку SMS оператором/MAX. Зафиксированный `timeouterror` ровно через пять минут вызван ожиданием значения из веб-формы (`asyncio.wait_for(..., timeout=300)`) и не доказывает сбой SMS. В предыдущей переписке ответ был слишком уверенно назван проблемой доставки; причина пока не установлена. Успех `web.max.ru` и локального PyMax подтверждает работоспособность номера, но эти входы используют другой запрос и условия сети.

Для следующей **одной** контролируемой попытки нужны безопасные метки этапов: выбранный `proxy_id`, время начала и завершения соединения, факт ответа `request_code` (`token_set`, без самого токена), переходы `waiting_code`/`verifying_code`, класс ошибки и длительность. Текущий `log_level="WARNING"` (`maxbot_v2/max_adapter.py:45`) и сохранение лишь `timeouterror` не позволяют локализовать причину. Не писать в логи номер, код, пароль или URL прокси. Если ответ снова придёт без SMS, отдельно сравнить минимальный скрипт PyMax 2.4.1 на ПК через **тот же** прокси с уже успешным запуском без прокси, меняя только маршрут. Повторные SMS-запросы выполнять с паузой, чтобы не спутать сетевую проблему с ограничением MAX. Пока этого измерения нет, «виноват прокси» остаётся гипотезой.

## Дополнительные эксплуатационные риски

- `Dockerfile` задаёт `--proxy-headers`, но не задаёт `--forwarded-allow-ips`. [Uvicorn по умолчанию доверяет только `127.0.0.1`](https://www.uvicorn.org/settings/), а Caddy соединяется из другого контейнера. Вывод по конфигурации: `request.client.host` может быть одним IP Caddy для всех гостей, поэтому лимит в 5 запусков за 15 минут (`maxbot_v2/app.py:449-451`) становится общим для группы; `request.base_url` может выдать `http://` ссылку (`app.py:290`). Проверить через безопасный диагностический запрос на VDS и настроить доверие только к Caddy. Публичный HTTPS адрес можно брать из явно заданного `DOMAIN`, без зависимости от входящих заголовков.
- `EncryptedSessionFile.open()` и `.seal()` используют один и тот же временный SQLite-файл аккаунта (`maxbot_v2/session_vault.py:21-55`). Одновременная работа воркера и ручной «Проверить назначение» (`maxbot_v2/app.py:669-705`) может перезаписать/удалить файл активного клиента. Это риск по коду, без воспроизведённого сбоя. Нужна одна блокировка на аккаунт на время `open → connect → close → seal`.
- В опубликованной переписке присутствует действующая гостевая ссылка. После исправления выдачи ссылки её следует заменить штатной кнопкой, чтобы старый токен перестал работать. Сам токен здесь не приводится.

## Удобство без расширения архитектуры

1. В карточке группы постоянно показывать статус ссылки подключения и кнопку «Показать / копировать». Добавить простой `GET /api/groups/{id}/onboarding-link` только для владельца: он возвращает текущую ссылку из уже зашифрованного токена без создания новой. Рядом отдельные «Заменить» и «Отозвать», срок и число использований. После обновления страницы ссылка должна оставаться доступной владельцу.
2. В карточке группы добавить поле «Добавить прокси списком»: один `http://` или `socks5://` URL на строку, подписи создавать автоматически с возможностью переименования. Сервер проверяет все строки и добавляет их одной транзакцией: либо все, либо ни одной. Показать номера ошибочных строк. Сохранить нынешнее распределение по наименьшей загрузке.
3. Показывать подключение номера как короткую последовательность: запрос SMS → ввод кода → пароль 2FA при необходимости → вступление в группу → готово. Указывать, что код приходит по SMS; сохранять состояние формы при опросе. Для `failed` давать безопасную кнопку повтора, а не инструкцию править SQLite.
4. На карточке номера показывать назначенный день, прокси, статус текущей недели и понятную причину блокировки. Кнопки, которым ещё не хватает данных, отключать с кратким пояснением.

3. Добавить групповой ввод прокси, затем тесты атомарности и назначения. Реальное соединение с MAX не требуется для проверки UI и базы.
4. Собрать безопасную диагностику одного входа через назначенный прокси; только после неё решать, нужны ли изменения транспорта. Проверить ссылку `https://`, отдельные лимиты посетителей и блокировку сессии аккаунта.

Критерии готовности: без входа видна только форма входа; текущая ссылка копируется после обновления страницы и у каждой из двух групп отдельно; повтор неудачного входа не требует ручного удаления; поле кода не теряет фокус и текст; остановленная группа остаётся остановленной после сохранения названия; список прокси сообщает об ошибке; один список прокси импортируется атомарно; причина сбоя SMS локализуется по этапу и маршруту без раскрытия секретов.
