# Эксплуатация

## PyMax и прокси

PyMax вызывается только через единственный адаптер. В гостевой авторизации единственное исключение — один прямой вызов `request_code` временным клиентом с `proxy=None` и `persist_session=False`. До него приложение должно разрешить назначенный аккаунту включённый прокси и расшифровать его URL; если это не удалось, остановите сценарий до запроса кода. Ответ челленджа хранится в памяти процесса. `send_code`, `check_password`/2FA, установление и сохранение сессии, проверка членства и все прочие действия выполняются через основной клиент с назначенным прокси. Ошибка прокси не разрешает прямой переход. Не повторяйте автоматически `request_code` после таймаута или неопределённого результата. Ответ MAX подтверждает принятие запроса, но не доставку SMS.

Для диагностики используйте безопасные INFO/WARNING-события приложения: ID попытки, аккаунта и прокси, этап `request_code` / ожидания ввода / `send_code` / 2FA, длительность и класс ошибки. Приложение выводит эти события в stderr контейнера; отберите их командой `docker compose logs --since 15m --no-log-prefix app | grep -E 'onboarding_stage|onboarding_code_request|onboarding_failed'`. Различайте прямой `request_code` и последующие этапы через прокси; ответ PyMax не подтверждает доставку SMS. Не включайте подробные логи PyMax без фильтрации: они могут содержать URL прокси. Проверяйте по одному условию за раз и соблюдайте лимиты MAX. Не повторяйте запрос кода при неопределённом исходе.

Для отдельной ручной проверки доставки адаптер принимает необязательные `hold_open_until` и `response_received` в `PyMaxAdapter.request_code_direct`. После единственного ответа `request_code` временное прямое соединение остаётся открытым до сигнала события; код не проверяется, сессия не сохраняется, результат не повторяется. Обычная гостевая авторизация не передаёт эти события и сохраняет прежнее поведение. Одноразовая команда `python -m scripts.probe_code_delivery 82` (82 — ID согласованного тестового аккаунта) сначала читает SQLite только на чтение, проверяет `global_stop=1`, ожидающий аккаунт, отсутствие активной гостевой попытки, назначение включённого прокси той же группы и расшифровку URL, затем проверяет TCP-доступ через прокси и повторно сверяет назначение. Она делает один прямой запрос через адаптер, выводит `RESPONSE_RECEIVED` после ответа MAX, держит соединение открытым 90 секунд и выводит только безопасные поля. Код не вводите в гостевую форму. Если соединение закрылось до сигнала, проба завершается `direct_probe_connection_closed`; при таймауте ответ неопределённый, запрос не повторяют.

Для проверки без выпуска кода в действующий контейнер извлеките **оба файла одного и того же проверенного commit** в `/tmp` VDS и подключите их только в одноразовый контейнер с текущим образом и томом. На хосте из действующего Compose-каталога (после сверки SHA и остановки отправок):

```sh
git fetch origin codex/otp-held-probe
probe_sha=$(git rev-parse --verify origin/codex/otp-held-probe)
git show "$probe_sha:maxbot_v2/max_adapter.py" > /tmp/maxbot-held-adapter.py
git show "$probe_sha:scripts/probe_code_delivery.py" > /tmp/maxbot-held-probe.py
chmod 644 /tmp/maxbot-held-adapter.py /tmp/maxbot-held-probe.py
docker compose run --rm --no-deps -T \
  -v /tmp/maxbot-held-adapter.py:/app/maxbot_v2/max_adapter.py:ro \
  -v /tmp/maxbot-held-probe.py:/app/scripts/probe_code_delivery.py:ro \
  app python -m scripts.probe_code_delivery 82
```

Команда выполняет **один** запрос. Не повторяйте её при неопределённом результате. Событие `RESPONSE_RECEIVED` означает ответ MAX и начало 90-секундного наблюдения; после `HOLD_FINISHED` можно сообщить, пришёл ли код. Отсутствие кода при подтверждённо открытом соединении исключает немедленное закрытие как достаточное объяснение, но само по себе не доказывает блокировку по IP VDS. Не публикуйте телефон, код, токен, ключ или URL прокси.

## Выпуск и резервное копирование

Работайте через авторизованную консоль провайдера, которую открывает владелец. До выпуска установите действующие Compose-каталог, образ, том, SHA и состояние отправок; не копируйте секреты в чат или Git. На VDS маршрутизация задаётся приложением: один `request_code` с IP VDS, последующие действия через назначенный прокси. Проверка соединения с прокси обязательна до запроса кода. Изменение назначения или адреса после ожидания блокировки останавливает действие без прямого обхода. Автовступление проверяет chat ID и членство, а при неудаче оставляет вход и состояние `needs_membership` для ручной проверки.

Перед обновлением проверьте конкретный SHA `main`, конфигурацию Compose, версию контейнера, состояние тома и логи. Убедитесь, что кнопка остановки выключила новые отправки. Затем штатно остановите приложение и сделайте общий архив SQLite и зашифрованных session files:

```sh
docker compose stop app
install -d -o 10001 -g 10001 -m 700 /root/maxbot-backups
docker compose run --rm --no-deps -v /root/maxbot-backups:/backup app python scripts/backup.py /backup/maxbot-$(date -u +%F-%H%M%S).zip
```

Архив содержит SQLite snapshot и только зашифрованные файлы сессий. Каталог на хосте должен быть доступен UID `10001`, под которым работает приложение: иначе `backup.py` не сможет создать временный SQLite-файл и архив. Проверьте ZIP и скачайте копию за пределы VDS **до выпуска**, чтобы потеря сервера не уничтожила единственную копию. Храните `DATA_ENCRYPTION_KEY`, `APP_SECRET_KEY` и пароль владельца в отдельном секретном хранилище, отдельно от архива и Git.

До переключения трафика восстановите копию в пустую отдельную директорию, доступную UID `10001`, и проверьте `PRAGMA integrity_check`. Не подключайте восстановленный каталог к production. Проверьте чтение аккаунтов и сессий при том же `DATA_ENCRYPTION_KEY`, затем удалите тестовую среду с расшифрованными сессиями после фиксации результата.

При сборке передайте полный SHA в аргумент `BUILD_REVISION`, например `BUILD_REVISION=<main-SHA> docker compose build app`. Сохраните прежний образ и Compose-конфигурацию для отката, обновите приложение с сохранением рабочего тома. `/health` возвращает установленный `revision`. Сверьте его с GitHub SHA и локальным checkout из консоли и независимым HTTPS-запросом. Проверьте контейнеры, HTTPS, Caddy, заголовки клиентского IP и то, что порт приложения не опубликован напрямую. Не меняйте Caddy до успешной проверки восстановления. Отправки оставьте остановленными до проверки аккаунтов и ручного запуска владельцем.

## Проверка PyMax при выпуске

OTP и облачный пароль вводятся владельцем только в форме. На тестовом аккаунте проверьте автоматическое вступление, подтверждение членства, сохранение зашифрованной сессии и повторное подключение после рестарта. Если вступление не удалось, проверьте сохранение входа, состояние `needs_membership` и ручную проверку после вступления. Тестовую отправку проводите отдельно, лишь после проверки адресата и текста.

Сравните для успешного локального запуска и VDS версию/путь Python, `maxapi-python==2.4.1`, версию Android-клиента MAX, наличие сохранённой сессии и назначенный прокси. Последовательно проверьте локально без прокси, локально с прокси, на VDS, затем в веб-интерфейсе. Для каждого шага сохраните безопасные журналы и не включайте код, токен, пароль, телефон или URL прокси.

Реальную SMS-авторизацию и тестовую отправку проводите только на согласованном тестовом аккаунте и в тестовой группе. Одна ручная проверка на VDS подтвердила доставку кода, проверку кода и 2FA через тестовый SOCKS5, а также подключение PyMax; сессия была непостоянной и после процесса не сохранялась. Это не подтверждает работу раздельных маршрутов в веб-панели, членство или повторный вход после рестарта. Перед тестовым сообщением отдельно проверьте адресата и содержимое.

## Откат

Не очищайте том и не пересоздавайте базу для отката. Остановите отправки, сохраните текущий архив, верните предыдущий проверенный образ и конфигурацию, затем сверьте `/health` и журнал операций. Архивирование или удаление старых веток/worktree — отдельная операция после сверки Git и сохранения пользовательских файлов.
