# Эксплуатация

## PyMax и исходящие IP VDS

PyMax вызывается только через `maxbot_v2/max_adapter.py` и закреплён на `maxapi-python==2.4.1`. Вход выполняет один клиент со стандартным `SmsAuthFlow`: `request_code`, ввод OTP, `send_code`, при challenge — `check_password`, затем подтверждение профиля и сохранённой сессии. Все TCP-соединения этого клиента, проверки членства и отправки привязаны к назначенному исходящему IP VDS. Перед открытием TCP и каждым кадром адаптер повторно проверяет, что аккаунт закреплён за тем же включённым и доступным IP и что адрес присутствует на хосте. Отключение, исчезновение или переназначение IP прерывает текущую попытку; обхода или переключения на другой адрес нет. `62.109.10.109` запрещён для MAX, начальный рабочий адрес — `62.109.20.186`. Не повторяйте автоматически `request_code` после таймаута или неопределённого результата; его ответ не подтверждает доставку SMS.

Для диагностики используйте безопасные INFO/WARNING-события приложения: ID попытки, аккаунта и IP, этап, длительность и класс ошибки. Их можно выбрать командой `docker compose logs --since 15m --no-log-prefix app | grep -E 'onboarding_stage|onboarding_failed'`. Телефон, OTP, пароль, токен и сырые ошибки PyMax не записываются. Ошибка `error.profile.active.session.no2fa` означает ограничение MAX после OTP: сохраните аккаунт для ручной повторной попытки после установки пароля; код автоматически не запрашивайте. Пока проверяется пароль, API отвечает состоянием `verifying_password` и отклоняет повторную отправку; если PyMax снова запросит пароль, форма объяснит, что предыдущий не подошёл. Таймаут ввода кода/пароля отличается от сетевого таймаута.

`auth_state` показывает именно авторизацию (`unverified`, `authenticated`, `reauth_required`), а `accounts.status` — подключение к группе. PyMax сначала создаёт рабочую SQLite; сама по себе она не доказывает вход. Постоянная сессия записывается только после наличия строки с токеном, через консистентный SQLite backup и атомарную зашифрованную замену. Пустая база после запроса кода не сохраняется, предыдущие сессии и поколения не удаляются. При явном PyMax-отказе `FAIL_LOGIN_TOKEN`/`FAIL_LOGOUT_ALL` аккаунт блокируется до ручного входа, в том числе если отказ возник на ранее подключённом номере во время отправки или проверки группы. Следующий ручной старт в исходной группе сохранит новое поколение сессии; назначенный IP останется прежним, старая попытка членства будет отменена. Сетевые ошибки не инициируют ротацию. Для одноразовой гостевой ссылки существующее `waiting_membership` этого номера переиспользует своё место при таком восстановлении.

Счётчик IP `assigned_count` показывает все закрепления, включая старые ошибки. `authenticated_count`, `in_progress_count` и `unconfirmed_count` объясняют их состояние; неподтверждённые ошибки не входят в нагрузку при выборе IP для нового аккаунта. Повтор существующего номера переиспользует назначение.

## Выпуск и резервное копирование

Работайте через авторизованную консоль провайдера, которую открывает владелец. До выпуска установите действующие Compose-каталог, образ, том, SHA и состояние отправок; не копируйте секреты в чат или Git. Приложение и Caddy работают в сети хоста: Caddy занимает 80/443, приложение слушает только `127.0.0.1:8000`. До переключения убедитесь, что 80/443 свободны и локальный Caddy сможет обращаться к приложению. На VDS проверьте `ip -4 -br addr` и `curl -4sS --interface 62.109.20.186 https://api.ipify.org`; адрес `62.109.10.109` может оставаться для HTTPS-панели, но не для MAX. В панели «Обновить IP» обнаруживает и проверяет адреса, новые появляются выключенными; владелец включает их вручную. Смена IP аккаунта тоже ручная.

Перед обновлением проверьте конкретный SHA `main`, конфигурацию Compose, версию контейнера, состояние тома и логи. Убедитесь, что кнопка остановки выключила новые отправки. Затем штатно остановите приложение и сделайте общий архив SQLite и зашифрованных session files:

```sh
docker compose stop app
install -d -o 10001 -g 10001 -m 700 /root/maxbot-backups
docker compose run --rm --no-deps -v /root/maxbot-backups:/backup app python scripts/backup.py /backup/maxbot-$(date -u +%F-%H%M%S).zip
```

Архив содержит SQLite snapshot и только зашифрованные файлы сессий. Каталог на хосте должен быть доступен UID `10001`, под которым работает приложение: иначе `backup.py` не сможет создать временный SQLite-файл и архив. Проверьте ZIP и скачайте копию за пределы VDS **до выпуска**, чтобы потеря сервера не уничтожила единственную копию. Храните `DATA_ENCRYPTION_KEY`, `APP_SECRET_KEY` и пароль владельца в отдельном секретном хранилище, отдельно от архива и Git.

До переключения трафика восстановите копию в пустую отдельную директорию, доступную UID `10001`, и проверьте `PRAGMA integrity_check`. Не подключайте восстановленный каталог к production. Проверьте чтение аккаунтов и сессий при том же `DATA_ENCRYPTION_KEY`, затем удалите тестовую среду с расшифрованными сессиями после фиксации результата.

При сборке передайте полный SHA в аргумент `BUILD_REVISION`, например `BUILD_REVISION=<main-SHA> docker compose build app`. Сохраните прежний образ и Compose-конфигурацию для отката, обновите приложение с сохранением рабочего тома. `/health` возвращает установленный `revision`. Сверьте его с GitHub SHA и локальным checkout из консоли и независимым HTTPS-запросом. Проверьте контейнеры, HTTPS, Caddy, заголовки клиентского IP и то, что порт приложения не опубликован напрямую. Не меняйте Caddy до успешной проверки восстановления. Отправки оставьте остановленными до проверки аккаунтов и ручного запуска владельцем.

После запуска убедитесь в консоли VDS, что `ss -ltnp` показывает `127.0.0.1:8000`, а не `0.0.0.0:8000`; извне отдельно проверьте отказ подключения к `<домен>:8000`. Сверьте `curl -fsS http://127.0.0.1:8000/health` и HTTPS `/health` с SHA образа. В панели проверьте, что `62.109.20.186` доступен и включён, существующие аккаунты получили его назначение, а `62.109.10.109` не появился в пуле. Приобретённые позже IP должны появляться выключенными; включайте их вручную только после проверки исходящего адреса. При исчезновении назначенного IP не включайте отправки до восстановления или ручного переназначения.

## Проверка PyMax при выпуске

OTP и облачный пароль вводятся владельцем только в форме. На тестовом аккаунте проверьте автоматическое вступление, подтверждение членства, сохранение зашифрованной сессии и повторное подключение после рестарта. Если вступление не удалось, проверьте сохранение входа, состояние `needs_membership` и ручную проверку после вступления. Тестовую отправку проводите отдельно, лишь после проверки адресата и текста.

Сравните для успешного локального запуска и VDS версию/путь Python, `maxapi-python==2.4.1`, назначенный IP и наличие сохранённой сессии. На VDS подтвердите полный вход тестового профиля, сохранение и повторное открытие зашифрованной сессии, членство, а отдельной проверкой — тестовую отправку с ID ответа. Не включайте в журналы код, токен, пароль или телефон.

Реальную SMS-авторизацию и тестовую отправку проводите только на согласованном тестовом аккаунте и в тестовой группе. Ранее код приходил при ручном запуске PyMax через `62.109.20.186`, но вход завершился ошибкой `error.profile.active.session.no2fa`. Это подтверждает доставку OTP через новый IP, но не успешный вход панели, сохранение сессии, членство или отправку. До полного теста отправки оставьте остановленными.

## Откат

Не очищайте том и не пересоздавайте базу для отката. Остановите отправки, сохраните текущий архив, верните предыдущий проверенный образ и конфигурацию, затем сверьте `/health` и журнал операций. Архивирование или удаление старых веток/worktree — отдельная операция после сверки Git и сохранения пользовательских файлов.
