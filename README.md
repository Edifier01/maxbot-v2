# MAXBOT v2

Однопользовательская панель на FastAPI, SQLite и обычном JavaScript для планирования сообщений в MAX-группах. Проект сохраняет данные и зашифрованные сессии из существующего `/data`; перед выпуском всё равно создайте и проверьте резервную копию. Поддерживаемая схема базы расширяется повторяемо без удаления пользовательских строк.

## Состояние

PyMax закреплён на `maxapi-python==2.5.0` и изолирован в `maxbot_v2/max_adapter.py`. Вход использует один клиент со стандартным `SmsAuthFlow`; исходный IPv4 VDS проверяется перед TCP-соединением и каждой отправкой кадра. Для входа и членства он используется напрямую, для отправки — как источник подключения к закреплённому внешнему SOCKS5. Отключение, исчезновение или переназначение адреса останавливает текущую попытку без перехода на другой IP. Старый `62.109.10.109` запрещён для MAX; первым рабочим адресом служит `62.109.20.186`. В коде проекта нет требования к отдельному файлу разрешения или договору.

Автоматические проверки используют отдельную SQLite и фиктивный PyMax. Они не доказывают доставку SMS или работу конкретного IP/MAX-аккаунта. Реальную проверку проводите на тестовом номере и группе с согласованным содержимым. После выпуска `/health` возвращает `revision` образа; значение `unknown` означает, что SHA не был передан при сборке.

## Разработка

При создании группы панель сразу создаёт гостевую ссылку на 7 дней без лимита подключений. Открытие ссылки не обращается к MAX и не назначает IP: IP выбирается транзакционно после нажатия «Начать подключение», до запроса кода. Выбирается наименее загруженный включённый доступный адрес; при равной нагрузке — тот, которому дольше всего не назначали попытку. Пока попытка идёт, адрес не меняется. Гость вводит ФИО и российский номер в виде `+7XXXXXXXXXX`, `7XXXXXXXXXX`, `8XXXXXXXXXX` или 10 цифр; пробелы, скобки и дефисы допускаются. Сервер передаёт в PyMax только `+7XXXXXXXXXX`. После OTP и, если MAX запросил пароль, 2FA-приложение сразу блокирует повторную отправку формы, пока PyMax не запросит пароль снова; повторный challenge сообщает, что MAX отклонил предыдущий пароль. После входа и сохранения подтверждённой сессии панель пытается вступить в группу. Если вступление не удалось, авторизация остаётся сохранена в `needs_membership` и доступна до окончания или отзыва гостевой ссылки, в том числе после рестарта; живая попытка сохраняет данные, необходимые для ручной проверки членства. При сетевом сбое первой проверки членства форма сохраняет возможность ручной проверки после восстановления связи. До подтверждения членства отправки запрещены.

После двух подряд неверных облачных паролей MAX повторное подключение номера блокируется на 24 часа со второго отказа. Верный пароль сбрасывает счётчик. Сетевые ошибки и таймауты его не меняют. Блокировка действует на номер во всех группах и сохраняется после перезапуска.

Если MAX требует установить облачный пароль, гостевая форма показывает путь в приложении на телефоне. Откройте «Настройки» → «Безопасность» → «Пароль для входа», установите пароль и вернитесь к кнопке «Повторить подключение».

Администратор подключает номер кнопкой «Добавить номер» в карточке нужной группы: в новой вкладке открывается форма ФИО, телефона, OTP и, при необходимости, пароля MAX. Кнопка использует текущую ссылку подключения; если она недоступна, сначала создайте новую в той же карточке. IP-адреса показаны в сворачиваемом списке, закрытом по умолчанию: заголовок показывает общее число и число включённых адресов, раскрытие открывает обновление и управление IP.

Новые ссылки подключения имеют вид `/j/<код>` с 8-символьным случайным кодом из цифр и заглавных букв без похожих `I`, `L`, `O`, `U` (40 бит). При ручном вводе регистр букв не важен. Уже выданные ссылки `/join/<токен>` и прежние 22-символьные `/j/<токен>` продолжают работать и не заменяются при просмотре карточки. Новый код появляется при создании группы, после истечения прежней ссылки или при её явной замене.

Нужны Python 3.12 и Node.js 24. В Windows создайте окружение и установите зависимости разработки:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe -m pytest -q --ignore=tests/test_browser_workflows.py
.\.venv\Scripts\python.exe -m pytest -q tests/test_browser_workflows.py
node --check static/app.js
node --check static/join.js
node --test tests/test_join_start.cjs
```

На Linux установите браузер вместе с системными пакетами командой `python -m playwright install --with-deps chromium`. Запускайте обычные Python-тесты и Playwright отдельными командами: синхронный драйвер Playwright управляет циклом событий своего процесса. CI проверяет обе группы на Windows и Linux, JavaScript и сборку Docker на Linux. `requirements-dev.txt` содержит тестовые инструменты; производственный образ устанавливает только `requirements.txt`.

Создайте локальный `.env` из `.env.example`. Задайте уникальные `APP_SECRET_KEY`, `DATA_ENCRYPTION_KEY` и `OWNER_PASSWORD_HASH`. Хеш начального пароля создаётся интерактивно:

```powershell
.\.venv\Scripts\python.exe scripts/hash_password.py
```

Не сохраняйте секреты и реальные номера в Git или тестовых данных. Для первого локального запуска используйте отдельный каталог данных. Docker-режим запускается так:

```powershell
$env:BUILD_REVISION = (git rev-parse HEAD)
docker compose up -d --build
```

Caddy и приложение работают в сети хоста VDS. Caddy обслуживает 80/443, а приложение слушает только `127.0.0.1:8000`. Проверьте извне, что порт 8000 закрыт.

У номера одна постоянная пара дней отправки по Москве — понедельник и четверг, вторник и пятница или среда и суббота. Планировщик готовит по пять сообщений на каждый из двух дней. В воскресенье отправок нет. Откройте «Группы» → «Номера», чтобы увидеть ФИО, назначенные дни и прогресс. Группы с одним чатом MAX отправляют по очереди и сохраняют собственные ссылки и списки ФИО. Расписание фиксировано. Кнопки «Запустить» и «Остановить» управляют отправкой, после перезапуска нужен ручной запуск.

## PyMax

Используется `maxapi-python==2.5.0`. Ссылки на первичную документацию: [Client](https://docs.pymax.org/client.html), [SmsAuthFlow](https://github.com/MaxApiTeam/PyMax/blob/v2.5.0/src/pymax/auth/sms.py), [ExtraConfig](https://docs.pymax.org/api/client-config.html), [Messages](https://docs.pymax.org/messages.html) и [релиз PyMax 2.5.0](https://github.com/MaxApiTeam/PyMax/releases/tag/v2.5.0). Ссылки MAX-групп должны содержать `/join/`. Интеграция использует неофициальный API MAX.

Ответ PyMax на `request_code` подтверждает ответ MAX, но не доставку SMS. В журнале отдельно видны ответ на запрос кода, ожидание ввода OTP и сетевая ошибка; номер и причина подключения доступны только в авторизованном «Журнале» владельца. Диагностический номер хранится зашифрованным. OTP, пароль, токен и сырые ответы в журнал не попадают. Не повторяйте автоматически запрос с неопределённым результатом и соблюдайте лимиты MAX. Если новая попытка не завершилась подтверждённой авторизацией, после закрытия PyMax аккаунт, назначение IP и файлы этой попытки очищаются, а номер можно добавить заново как новый аккаунт. Если ранее авторизованный аккаунт требует повторного входа, его не удаляют автоматически. Сессия считается авторизованной только после профиля PyMax и атомарного зашифрованного SQLite-снимка с токеном. Пустая база не заменяет сохранённую сессию; явный отказ MAX `FAIL_LOGIN_TOKEN`/`FAIL_LOGOUT_ALL` требует нового поколения при следующем ручном запуске. Если MAX отклоняет сохранённый токен подключённого номера, авторизация блокируется; владелец может вручную переподключить номер в той же группе, сохранив IP и прежние поколения.

Панель проверяет публичные IPv4 при старте и ежедневно. Кнопка «Обновить IP» запускает проверку вручную. Рабочие адреса включаются автоматически. Назначенный IP сохраняется за аккаунтом и повторно используется при его переподключении. Для новых назначений балансируются авторизованные аккаунты и действующие попытки; старые ошибки не увеличивают нагрузку. Панель отдельно считает сохранённые номера и активные попытки. Кнопка «Удалить номер и сессию» удаляет все поколения сессий и временную SQLite после закрытия клиента, но оставляет обезличенный ID и историю. При `in_flight` или `unknown` отправке удаление возвращает конфликт до ручной сверки. В панели IP и списке группы видны назначения, авторизация, активные попытки и другие неподтверждённые номера. Для каждого IPv4 откройте «Прокси» и добавьте внешние SOCKS5 вручную или загрузите TXT до 30 строк за раз. Аккаунт получает наименее загруженный включённый и проверенный прокси своего IPv4 после входа, ранее авторизованный номер — при первой отправке. Прокси автоматически включается после успешной проверки SOCKS5 и TLS до MAX из пула нужного IPv4. Панель хранит закрепление при временном сбое. В «Номера» владелец может явно переназначить прокси того же пула. Исторические прокси и их назначения хранятся отдельно.

Панель перепроверяет SOCKS5 через 24 часа после последней проверки, в том числе при остановленных отправках. Ошибка приостанавливает отправки через этот прокси. Явное отключение в панели сохраняется после проверки и рестарта. Владелец может вручную сменить IPv4 или закрепить другой проверенный прокси из пула выбранного IPv4.

Для безопасного разбора старых неподключённых записей сначала подготовьте отчёт только по ID: `python -m scripts.cleanup_unverified_accounts`. Команда по умолчанию ничего не меняет; она пропускает живые/неоднозначные и завершённые успешные попытки, runtime-каталоги, авторизованные аккаунты, историю отправок и сессии с токеном или ошибкой чтения. Для старого формата `+8` отпечаток вычисляется по каноническому `+7`; если старое значение нельзя надёжно нормализовать и история отправок отсутствует, обезличенная запись остаётся без отпечатка. Применение требует явного `--apply --account-ids <ID...>` для каждого просмотренного номера и возвращает ненулевой код, если хотя бы один ID не был удалён. Не удаляйте записи только потому, что общий счётчик выше числа подключённых.

## Резервные копии и документы

На VDS исходящий адрес задаётся адаптером через привязку TCP-сокета. Внешний SOCKS5 открывает туннель, а PyMax устанавливает TLS до MAX поверх него. Назначение, включённость, доступность и наличие IP перепроверяются перед соединением и каждым запросом PyMax. Реальную доставку OTP, полный вход, повторное открытие сессии, членство и отправку подтверждает только отдельный тест на VDS с владельцем.

Архив включает SQLite snapshot и только зашифрованные файлы сессий. `DATA_ENCRYPTION_KEY` и секреты развёртывания храните отдельно. Порядок резервного копирования и восстановления описан в [docs/operations.md](docs/operations.md).
