# Инструкции агентам MAXBOT v2

## Проект

Это компактная однопользовательская панель на Python 3.12, FastAPI, SQLite, обычном JavaScript, Docker Compose и Caddy. Сохраняйте эту архитектуру. Не добавляйте отдельные серверы, очереди, frontend-фреймворки или новую базу без конкретной необходимости и согласованного плана.

## Перед началом

1. Прочитайте этот файл, `docs/project-state.md`, `docs/specification.md`, `docs/operations.md` и последние записи `docs/change-log.md`. Старые аудиты в `docs/audit*.md` — исторический контекст; проверяйте описанные факты по текущему коду.
2. Проверьте `git status --short --branch`, `git branch -vv`, `git worktree list`, `git log --oneline --decorate -12` и `git remote -v`. Если сеть доступна, сравните нужную ветку с GitHub. Не переключайте чужую ветку, не выполняйте `reset --hard`, `clean -fd`, массовое удаление и не удаляйте worktree ради уборки.
3. Найдите тесты и маршрут/модуль, который меняете. Для исправления сначала добавьте тест, воспроизводящий ошибку.
4. Сохраните рабочие пользовательские файлы, SQLite, зашифрованные session files, секреты и локальные настройки. Перед изменением схемы или выпуска подготовьте и проверьте резервную копию.

## Правила проекта

- PyMax остаётся на `maxapi-python==2.4.1` и вызывается только через `maxbot_v2/max_adapter.py`. Вход использует один клиент и стандартный `SmsAuthFlow` с провайдерами веб-формы. Сначала сверяйте последовательность вызовов с этой версией библиотеки и `docs/operations.md`.
- Каждому аккаунту закреплён один включённый и доступный публичный IPv4 VDS. Все его TCP-соединения с MAX, включая запрос кода, OTP, 2FA, членство и отправку, привязываются к нему в адаптере; при ошибке запрещён переход на другой IP. `62.109.10.109` запрещён для MAX. Новые IP после обнаружения выключены до ручного включения владельцем. При исчезновении или отключении адреса аккаунт блокируется до восстановления либо ручного переназначения. Не повторяйте неопределённый `request_code` автоматически.
- Не выводите телефоны, OTP, пароли, токены и содержимое ссылок с секретами в UI, audit log и обычные логи. Диагностика содержит только безопасный ID попытки/аккаунта/IP, этап, длительность, наличие ответа и класс ошибки.
- Ответ на `request_code` PyMax не доказывает доставку SMS. Не объявляйте реальную авторизацию или MAX-интеграцию проверенной по фиктивному адаптеру, unit-тестам или одному `/health`.
- Отправка получает статус `accepted` только при подтверждении MAX с ID. Доказанный отказ до отправки можно повторить; таймаут, отмена в полёте и любой неопределённый результат — `unknown`, без автоматического повтора. Перед ручной сверкой не удаляйте операции и слоты.
- Изменения расписания, назначения IP и состояния должны повторно проверяться перед каждой отправкой и попыткой повтора. Ручной стоп управляет текущей работой; `auto_run` — только поведением после рестарта.
- Существующие таблицы и зашифрованные session files сохраняются. Изменения схемы выполняйте повторяемо, без удаления или пересоздания пользовательских данных. Ключ шифрования никогда не храните в Git или рядом с резервной копией.
- В браузерном хранилище гостя разрешён только ID попытки. Не сохраняйте OTP, пароль MAX или токен авторизации.

## Проверки

Windows PowerShell:

```powershell
py -3.12 -m pip install -r requirements-dev.txt
py -3.12 -m playwright install chromium
py -3.12 -m pytest -q --ignore=tests/test_browser_workflows.py
py -3.12 -m pytest -q tests/test_browser_workflows.py
node --check static/app.js
node --check static/join.js
node --test tests/test_join_start.cjs
```

Linux устанавливает браузер командой `python -m playwright install --with-deps chromium`. Запускайте обычные Python-тесты и Playwright разными командами, чтобы синхронный драйвер браузера не разделял процесс с unit-тестами asyncio. CI проверяет обе группы и Chromium на Windows/Linux и собирает Docker на Linux. Автотесты должны работать на отдельной SQLite и фиктивном PyMax, без production-секретов, MAX-запросов и реальных сообщений.

Если проверка не запускалась из-за отсутствующей среды или браузера, явно укажите это; не заменяйте её предположением об успехе. Учитывайте точку входа и реальные кнопки UI, проверяйте мобильные ширины 390, 768 и 1440 px и клавиатурное управление.

## Документация и передача

Каждое изменение кода или конфигурации сопровождайте актуализацией затронутых разделов README/specification/operations и записью в `docs/change-log.md` **в том же PR**. Если поведение не изменилось, прямо отметьте это в записи. Укажите дату, PR или commit, что поменялось, зачем, фактические команды проверки, оставшиеся ограничения и состояние VDS. Обновляйте `docs/project-state.md`, если изменились архитектура, сценарии, ограничения или известные проблемы. Не называйте VDS обновлённым, пока SHA не сверен с `/health`.

Работа с GitHub: сверяйте ветки, `origin/main`, статусы и рабочие каталоги; работайте в изолированной ветке `codex/…`; добавляйте воспроизводящие тесты и исправления; открывайте PR; проверяйте итоговый diff и CI; после слияния сверяйте локальный `main` с GitHub. Не переключайте чужую ветку и не удаляйте существующие worktree ради уборки. Историческую реализацию из `1630ea6` можно использовать только после проверки отдельных изменений, без полного возврата отменённого PR.

Работа с VDS ведётся через авторизованную консоль провайдера, которую открывает владелец. Перед выпуском установите действующие Compose-каталог, образ, том, SHA и состояние отправок. Секреты не переносите в чат или Git. Остановите отправки и приложение; создайте общий архив SQLite и зашифрованных сессий, выгрузите копию за пределы VDS и проверьте восстановление отдельно (целостность SQLite и читаемость сессий существующим ключом). Соберите проверенный SHA `main` с `BUILD_REVISION`, сохраните предыдущий образ и конфигурацию для отката, обновите приложение с прежним томом. Проверьте контейнеры, HTTPS, закрытый внешний порт приложения и `/health.revision` из консоли и независимым запросом. Отправки остаются остановленными до проверки аккаунтов и ручного запуска владельцем.

В итоговом сообщении укажите фактическую проверку, ограничения и незавершённые действия. Отдельно различайте: тесты прошли; PR обновлён; GitHub `main` синхронизирован; установленная VDS-ревизия сверена; реальная авторизация MAX успешно проверена.
