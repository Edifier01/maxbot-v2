# Инструкции агентам MAXBOT v2

## Проект

Это компактная однопользовательская панель на Python 3.12, FastAPI, SQLite, обычном JavaScript, Docker Compose и Caddy. Сохраняйте эту архитектуру. Не добавляйте отдельные серверы, очереди, frontend-фреймворки или новую базу без конкретной необходимости и согласованного плана.

## Перед началом

1. Прочитайте этот файл, `docs/project-state.md`, `docs/specification.md`, `docs/operations.md` и последние записи `docs/change-log.md`. Старые аудиты в `docs/audit*.md` — исторический контекст; проверяйте описанные факты по текущему коду.
2. Проверьте `git status --short --branch`, `git branch -vv`, `git worktree list`, `git log --oneline --decorate -12` и `git remote -v`. Если сеть доступна, сравните нужную ветку с GitHub. Не переключайте чужую ветку, не выполняйте `reset --hard`, `clean -fd`, массовое удаление и не удаляйте worktree ради уборки.
3. Найдите тесты и маршрут/модуль, который меняете. Для исправления сначала добавьте тест, воспроизводящий ошибку.
4. Сохраните рабочие пользовательские файлы, SQLite, зашифрованные session files, секреты и локальные настройки. Перед изменением схемы или выпуска подготовьте и проверьте резервную копию.

## Правила проекта

- PyMax закреплён на `maxapi-python==2.5.0` и вызывается только через `maxbot_v2/max_adapter.py`. Вход использует один клиент и стандартный `SmsAuthFlow` с провайдерами веб-формы. Сначала сверяйте последовательность вызовов с этой версией библиотеки и `docs/operations.md`.
- Каждому аккаунту закреплён один включённый и доступный публичный IPv4 VDS. Запрос кода, OTP, 2FA и проверки членства выполняются напрямую с этого IPv4. Плановые отправки, чтение публикаций канала и реакции используют закреплённый внешний SOCKS5 из общего пула. Сокет VDS → SOCKS5 привязывается к IPv4 аккаунта, MAX видит выходной IP прокси. Загружайте до 30 URL за операцию и храните каждый нормализованный URL зашифрованным отдельно от исторических прокси. Храните результат, время проверки, включённость и ручное отключение отдельно для каждой пары IPv4 и SOCKS5. Проверка использует привязанный TCP до прокси, SOCKS5 и TLS до MAX без открытия сессии аккаунта. Включайте рабочие IPv4 и маршруты SOCKS5 автоматически после успешной проверки при отсутствии ручного отключения. При отказе приостанавливайте конкретный маршрут. Сохраняйте явное отключение владельцем между проверками и рестартами. После входа закрепляйте наименее загруженный прокси из числа рабочих маршрутов с IPv4 аккаунта. У ранее авторизованного аккаунта создавайте назначение при первой операции через прокси. При сбое или смене IPv4 сохраняйте прокси, пока владелец не переназначит его. Используйте готовый маршрут с текущего IPv4 аккаунта. `62.109.10.109` запрещён для MAX. Не повторяйте неопределённый `request_code` автоматически.
- Полный номер показывайте только в журнале подключений авторизованного владельца. Храните его в отдельном зашифрованном поле, не выводите в гостевой API, audit log, список аккаунтов и обычные логи. OTP, пароли, токены и содержимое секретных ссылок не выводите в диагностику.
- Ответ на `request_code` PyMax не доказывает доставку SMS. Не объявляйте реальную авторизацию или MAX-интеграцию проверенной по фиктивному адаптеру, unit-тестам или одному `/health`.
- `accounts.auth_state` (`unverified`, `authenticated`, `reauth_required`) отделён от состояния членства в `accounts.status`; `ever_authenticated` не позволяет удалить ранее авторизованный аккаунт после ошибки повторного входа. Успешную авторизацию отмечайте только после профиля PyMax и сохранённого зашифрованного SQLite-снимка с непустым токеном. Ошибка вступления в группу после этого сохраняет авторизацию и живую попытку `waiting_membership`; телефон в ней нужен до завершения ручной проверки. Для остальных завершённых попыток телефон и ФИО очищаются. Пустую рабочую БД не сохраняйте и не заменяйте ею существующий файл. Для снимка используйте SQLite backup и атомарную зашифрованную замену, оставляя рабочую БД открытой PyMax до `close()`.
- Только явные PyMax `FAIL_LOGIN_TOKEN`/`FAIL_LOGOUT_ALL` требуют ротации сессии и блокируют отправки этого аккаунта. Следующий ручной запуск в исходной группе использует новое `session_generation`; старые поколения, аккаунт и IP сохраняются. Если отказ обнаружен у активного аккаунта, он доступен для такого ручного переподключения. Его прежний `waiting_membership` отменяется; если он занимал слот одноразовой ссылки, этот же слот переходит новой попытке. Сетевые ошибки не сбрасывают сессию. Авторизованный `waiting_membership` переживает рестарт и 15-минутный срок попытки, пока приглашение действительно.
- IP API сохраняет `assigned_count` для всех назначений и отдельно показывает сохранённые аккаунты, действующие попытки и остальные неподтверждённые назначения. Балансировка нового назначения учитывает авторизованные аккаунты и незавершённые попытки; исторические ошибки нагрузки не добавляют. При равной нагрузке выбирается IP, которому дольше всего не назначали попытку. Повтор существующего номера сохраняет прежний IP; новая регистрация после неудачи получает новое назначение.
- Новые неавторизованные попытки удаляются после отказа, отмены, истечения или прерывания процесса: PyMax закрывается, поколения сессии и IP удаляются, аккаунт обезличивается, телефон освобождается для нового ID. Ранее авторизованные аккаунты при ошибках повторного входа сохраняются. Удаление владельцем доступно только при отсутствии `in_flight`/`unknown` операций; `delete_pending` повторяется после рестарта, пока все файлы сессий не удалены. Историю, слоты и операции не удаляйте. Недельный лимит после повторной регистрации обеспечивайте HMAC-отпечатком номера, не выводя его в UI.
- Диагностика подключения хранит ID попытки, аккаунта, группы и IP, этап, результат, длительность, наличие ответа, класс ошибки и безопасную причину. Зашифрованный номер хранится отдельно для авторизованного журнала. Ответ MAX на запрос кода не доказывает доставку SMS. Старые неподтверждённые аккаунты анализируйте сначала `python -m scripts.cleanup_unverified_accounts` (dry-run из каталога проекта); не очищайте их по разнице счётчиков. Применение допускает только вручную перечисленные ID через `--apply --account-ids <ID...>` после резервного копирования и проверки каждого ID.
- Отправка получает статус `accepted` только при подтверждении MAX с ID. Доказанный отказ до отправки можно повторить. Таймаут, отмена в полёте и любой неопределённый результат дают `unknown` без автоматического повтора. Перед ручной сверкой не удаляйте операции и слоты. Все группы панели с одним `chat_id` используют общую очередь. Записывайте адресат при захвате операции и удерживайте не более одной операции `in_flight` на чат. Отдельные гостевые ссылки, группы и списки ФИО сохраняются.
- Каждому активному аккаунту назначается постоянная пара Пн/Чт, Вт/Пт или Ср/Сб по московскому календарю. Пять слотов в назначенный день, десять в неделю, в воскресенье отправок нет. Лимит номера продолжает действовать после повторной регистрации по HMAC. Учитывайте `accepted`, `unknown` и `in_flight` по времени начала операции. Проверяйте дату, пару дней, состояние аккаунта и сетевые назначения перед отправкой и безопасным повтором. Кнопки «Запустить» и «Остановить» управляют текущей работой. После рестарта отправки остановлены.
- Существующие таблицы и зашифрованные session files сохраняются. Изменения схемы выполняйте повторяемо, без удаления или пересоздания пользовательских данных. Ключ шифрования никогда не храните в Git или рядом с резервной копией.
- В браузерном хранилище гостя разрешён только ID попытки. Не сохраняйте OTP, пароль MAX или токен авторизации.

## Проверки

Windows PowerShell:

```powershell
py -3.12 -m pip install -r requirements-dev.txt
py -3.12 -m playwright install chromium
py -3.12 -m pytest -q --ignore=tests/test_browser_workflows.py
py -3.12 -m pytest -q tests/test_browser_workflows.py
node --check static/app.js
node --check static/join.js
node --test tests/test_join_start.cjs
```

Linux устанавливает браузер командой `python -m playwright install --with-deps chromium`. Запускайте обычные Python-тесты и Playwright разными командами, чтобы синхронный драйвер браузера не разделял процесс с unit-тестами asyncio. CI проверяет обе группы и Chromium на Windows/Linux и собирает Docker на Linux. Автотесты должны работать на отдельной SQLite и фиктивном PyMax, без production-секретов, MAX-запросов и реальных сообщений.

Если проверка не запускалась из-за отсутствующей среды или браузера, явно укажите это; не заменяйте её предположением об успехе. Учитывайте точку входа и реальные кнопки UI, проверяйте мобильные ширины 390, 768 и 1440 px и клавиатурное управление.

## Документация и передача

Каждое изменение кода или конфигурации сопровождайте актуализацией затронутых разделов README/specification/operations и записью в `docs/change-log.md` **в том же PR**. Если поведение не изменилось, прямо отметьте это в записи. Укажите дату, PR или commit, что поменялось, зачем, фактические команды проверки, оставшиеся ограничения и состояние VDS. Обновляйте `docs/project-state.md`, если изменились архитектура, сценарии, ограничения или известные проблемы. Не называйте VDS обновлённым, пока SHA не сверен с `/health`.

Работа с GitHub: сверяйте ветки, `origin/main`, статусы и рабочие каталоги; работайте в изолированной ветке `codex/…`; добавляйте воспроизводящие тесты и исправления; открывайте PR; проверяйте итоговый diff и CI; после слияния сверяйте локальный `main` с GitHub. Не переключайте чужую ветку и не удаляйте существующие worktree ради уборки. Историческую реализацию из `1630ea6` можно использовать только после проверки отдельных изменений, без полного возврата отменённого PR.

Работа с VDS ведётся через авторизованную консоль провайдера, которую открывает владелец. Перед выпуском установите действующие Compose-каталог, образ, том, SHA и состояние отправок. Секреты не переносите в чат или Git. Остановите отправки и приложение; создайте общий архив SQLite и зашифрованных сессий, выгрузите копию за пределы VDS и проверьте восстановление отдельно (целостность SQLite и читаемость сессий существующим ключом). Соберите проверенный SHA `main` с `BUILD_REVISION`, сохраните предыдущий образ и конфигурацию для отката, обновите приложение с прежним томом. Проверьте контейнеры, HTTPS, закрытый внешний порт приложения и `/health.revision` из консоли и независимым запросом. Отправки остаются остановленными до проверки аккаунтов и ручного запуска владельцем.

В итоговом сообщении укажите фактическую проверку, ограничения и незавершённые действия. Отдельно различайте: тесты прошли; PR обновлён; GitHub `main` синхронизирован; установленная VDS-ревизия сверена; реальная авторизация MAX успешно проверена.
